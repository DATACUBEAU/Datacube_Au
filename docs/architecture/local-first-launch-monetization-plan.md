# DataCube AU — zero-budget launch decision
Date: 2026-11-25. This decision supersedes earlier plans to activate cloud AI at launch.

## Scope
- Kotlin/Jetpack Compose is the active Android client; Room, WorkManager and local models remain the inference/document backbone.
- Local inference, RAG, study tools, voice, podcasts, document storage and previously authenticated offline access remain on-device.
- Cloud AI/OpenRouter, cloud credit wallets and credit purchases are deferred: UI status **Coming soon**. No provider call, automatic cloud fallback, cloud reservation, credit purchase or paid hosting for this launch. Preserve existing code for a separately reviewed future release. Do not delete historical billing records or invalidate existing subscriptions.
- Keep Supabase as the lightweight control plane for authentication, profiles, existing billing/admin and future server-authoritative rewards; Vercel for official download/sign-in and GitHub Actions/Releases for build/update distribution. Do not introduce paid infrastructure without an explicit budget and approval.

## Execution gates
1. Stabilize: offline cold start, RAG citations, native stop/stream controls, independent background jobs, model backup and restore, voice/podcast continuity, low-RAM and thermal performance. Physical device acceptance and signed APK verification remain mandatory.
2. Distribute: official website first, preserve package/signing identity and increasing version code; separate future store distribution channels. Existing GitHub release manifest and Android updater remain the current delivery path; a Supabase release manifest is a future design, not a launch prerequisite. Current personally signed test APK is not a store-ready production release.
3. Ads: design a centralized provider-neutral Ad Engine, with proposed websiteRelease/Start.io and supported-store flavor/AdMob. No ad SDK or provider account is activated in this change. Confirm provider approval, eligible publisher/account holder, genuine verification, age-appropriate consent and applicable platform rules before implementation. No ads on offline startup, authentication, document reading, generation or voice playback; no document/chat content sent for ad targeting. Network/provider failure must not block basic local features.
4. Rewards: optional, configurable server-authoritative grants with provider-specific verification, replay/idempotency protection, no rewards for clicks or artificial impressions. Replace rolling five-hour grants with feature-specific consumable units: one verified reward grants 1,800 seconds of actual podcast playback, 10 image submissions, or 10 voice-note submissions. Initial free allowance is two images and two voice notes per account; initial podcast allowance remains undecided. Smart Notes, text chat and document RAG remain free. No three-task prerequisite. Reward amounts require provider-policy review and product validation. Offline entitlements must be verifiable, scoped and fail safely; basic local features stay available.
5. Pro: proposed weekly/monthly ad-free eligible local premium features; price and payment/store policy to be decided. Preserve existing account and subscription management. Do not sell cloud access or credits while cloud is paused. Existing billing compatibility is not proof of native entitlement enforcement.
6. Cloud: only reopen after revenue/budget approval, security review, user consent for remote processing, server-side provider keys, bounded per-user and global spend, idempotent reservation/reconciliation, streaming/cancellation, and explicit operational kill switch. No cloud costs are authorized by this plan.

## Launch blockers
Physical-device validation, durable production signing, distribution/provider approvals and age/account eligibility, reward verification, native billing integration and local account isolation. Revenue projections are hypothetical, not launch forecasts. Start.io/AdMob availability and applicable marketplace/payment terms must be verified before shipping monetization. No changes to Supabase schema, provider credentials, billing or deployed infrastructure are needed for the Coming soon label.

## Offline consumable reward contract (design only; not activated)
- The backend owns grant issuance. Create an authenticated, single-use reward intent for one feature and a server-generated nonce, verify the provider's signed server callback, and atomically insert the grant with unique provider transaction ID and intent ID. Never credit the client completion callback alone. Confirm Start.io supports verifiable server callbacks before enabling rewards through that provider; do not substitute client claims.
- Allocate a bounded portion of the account's remaining balance to a single device lease in a server transaction, preventing two devices from spending the same units. Sign the lease server-side, bind to account, device key, feature, lease ID, units, policy version and expiration. No signing secret in Android. Keep the private device key in Android Keystore. Leases are issued online only and cannot create more units while offline.
- In Android persist lease and append-only consumption entries in Room; atomically reserve units before accepting an image or voice-note submission. Release reservations only for documented failed operations; deduplicate retries by operation ID. Podcast counts actual active playback seconds (not generation, pause or wall-clock time), reserving small persisted playback segments before play and stopping at exhaustion. Use monotonic elapsed time in each playback session, no reliance on changing the phone clock for consumption. Do not interrupt ongoing core text chat or reading.
- Reconcile usage idempotently when online, including account/device/lease ID and monotonically ordered sequence. Reissue only after the server verifies the unused balance; no automatic reset after reconnect/reinstall. Revoke compromised leases and cap unacknowledged allocation. No documents, images, voice recordings or chat text in the usage ledger. Display remaining image and voice counts and podcast minutes/seconds; lock only the exhausted premium action, with optional online reward and clear offline messaging.
- Threat model: server-authoritative rewards prevent forged online grants, not all local tampering. A modified APK can bypass local enforcement because model weights and inference run on-device. Keystore, signed leases and conservative offline allocations reduce casual abuse; never advertise unbreakable offline DRM. Define free-allocation reset cadence, multi-device/lease expiry policy, cancellation/refund semantics, provider approvals, age-appropriate ad consent and eligible publisher ownership before production activation. Do not promise a fixed 30-second ad duration.
- Cloud inference and credits remain Coming soon. No reward or ad SDK, database change, quota gate or billing activation in this design update.

## Native ads and reward operations
- Designated Home and Settings placements only, visibly labeled Advertisement and separated from ordinary controls. No forced refresh loop, background playback, deceptive clicks or native ad impressions counted as rewarded completions. Follow the provider's supported load/refresh and native rendering rules; destroy ad objects when the placement leaves the screen. Do not show ads without valid consent/eligibility, while offline, to ad-free members, or over chat, generation, reading or audio.
- Reward server foundation maps verified intents to fixed server-owned units; missing provider verification rejects the callback. Before enabling it, implement a provider-signature adapter and transactional storage with unique intent and provider transaction constraints, replay tests, signed offline leases and persistent consumption. No real grants are issued by the current unconnected module.
- Conex reward administration: owner-only read access to verified completion totals, distinct accounts, provider and feature breakdown, grants and reconciled consumption. Account-level drill-down should be limited to support/fraud resolution, with audit logging and minimal data. No chat content or recordings. Actual revenue comes from provider reports, not a fabricated value per completion.
- Student experience: use local source-grounded visual tables/flows/bar/pie charts only where appropriate; do not invent numerical values. Explicit memory writes remain user-controlled. Fast/Balanced/Deep are response and retrieval policies, not measured native reasoning budgets.
