# Mobile OAuth session exchange investigation

After the hosted Site URL was updated, a read-only aggregate of auth.flow_state confirmed a Google authorization on the custom domain using S256, with linked user, provider token received and auth_code_issued_at set. Three earlier Vercel-referrer flows also had issued codes. The recent token logs showed no PKCE exchange (only refresh exchanges in the wider window); mobile device requests had not reached approval. One separate 400 was an unknown provider, not evidence of a Google client-secret failure. No personal information or credentials were exported.

A concrete client-side race was found: stale auth cleanup can overlap new OAuth initiation, and forced reauthentication may repeat on SIGNED_OUT/user changes. Serialize cleanup and prevent it from deleting a newly generated verifier, guard callback bootstrap against overwriting fresh session state, and expose fixed failure-stage messages for mobile sign-in rather than redirecting through a generic error loop. Add an actual SDK-generated challenge/verifier browser regression with mocked provider return (not a live Google test). No database, hosted OAuth settings, provider secrets or Android changes. Live verification after release is mandatory; these findings do not conclusively prove the user's exact browser error.
